# 狐火の帳(Producer Check)設計仕様 — Step 5

**日付:** 2026-07-12
**状態:** 提案。ユーザー承認後に Phase A の縦切り実装へ進む。この文書だけを根拠に実装を開始しない
**対象:** Step 5「狐火の帳」— 作者が自分のデモ・ラフミックスを iPhone で確かめる一画面検聴

## 1. 目的

[PRODUCT_DIRECTION v3 §4.4](../../PRODUCT_DIRECTION.md) のとおり、作者自身が自分のデモやラフミックスを iPhone で軽く確かめたい、という実際の欲求のためだけに作る。市場や競合は理由にしない。

Step 4 の完了(2026-07-12、行列9体の40×48統一と視覚reducerの`main`統合)を受け、建設順序の次にあたる。Step 3(狐火の調律)は iOS 27 正式 SDK の再検証まで保留のままであり、**本機能は Step 3 に依存しない** — Core AI / Music Understanding / 外部ライブラリを使わず、オンデバイスの自前解析だけで成立させる。

## 2. 現在地

- §4.4 の機能はすべて未実装。
- 再生経路は `AVAudioPlayer` + 15 Hz `averagePower` のみ。PCM tap やオフライン解析経路はない。
- `AudioTrack` は `contentHash`(SHA-256)を持ち、`library.json` に永続化されている — 解析キャッシュのキーとして再利用できる。
- 取込は `ImportSummary` で成功・重複・失敗を表示する経路が実装済み — 共有シート取込(Phase D)はこの経路を再利用する。

## 3. 原則との整合(Pillars との突き合わせ)

- **音への敬意 / 音を勝手に加工しない:** 解析はオフラインの読み取り専用で、再生音は未加工のまま。唯一の例外は Phase B の A/B ラウドネスマッチで、帳の中の明示操作としてのみ再生音量を調整し、適用中は画面に明示、帳を閉じたら必ず解除する。元ファイルは書き換えない(非破壊)。
- **Local-first Trust:** すべてオンデバイス。音源も解析結果も外部送信しない。
- **共存規則(§3):** 帳が開いている間、夜行絵巻は静的な背景へ退き、数値が主役になる。助言の語彙は狐火で統一する。
- **提案の語彙:** 「補正」ではなく**「提案」**。すべての提案に根拠を付す(例:「True Peak が -0.1 dBTP を超えています。書き出し時のリミッタ余裕の確認を提案します」)。自動では何も直さない。
- **収集ゲームの線(§6):** 帳はトラック起点の表示のみ。妖怪起点の逆引きや網羅表示は作らない。
- **語彙表:** 画面は「狐火の帳(とばり)」、指標表示は「狐火の目盛」と呼ぶ。検聴は世界観の外に出ず、世界観は検聴の邪魔をしない。

## 4. Phase matrix

Step 4 の frame matrix と同様に、段階ごとにゲートを置く。**この仕様の承認は Phase A の着手だけを意味し、B〜D は各前段の検証後に順次進める。**

| Phase | 内容 | 出口条件 |
|---|---|---|
| A | オフライン解析エンジン + 一画面検聴(読み取り専用) | 既知テスト信号でのユニットテストGREEN、再生回帰なし、Simulator確認、ユーザー承認 |
| B | A/B 参照(ラウドネスマッチ付き) | マッチの適用・解除・表示が明示的で、帳の外に漏れない |
| C | チェックポイント(時刻付きメモ) | `library.json` 互換を保った永続化と読み書き |
| D | 共有シート /「このAppで開く」取込 | 既存 `ImportSummary` 経路での一手順取込 |

### 4.1 Phase A — 狐火の目盛(一画面検聴)

解析エンジン `KitsunebiAnalyzer` を新設する。`AVAudioFile` で PCM をチャンク読みし、次を算出する。

| 指標 | 定義 |
|---|---|
| Integrated Loudness | ITU-R BS.1770-4。K-weighting(2段biquad)、400 ms block・75% overlap、absolute −70 LUFS gate + relative −10 LU gate |
| Max Short-term | 3 s 窓の short-term loudness の最大値 |
| Sample Peak | 全チャンネルの絶対最大サンプル値(dBFS) |
| True Peak(近似) | 4x オーバーサンプリング(ITU-R BS.1770-4 Annex 2 準拠のFIR補間)による inter-sample peak(dBTP) |
| クリップ疑い | \|x\| ≥ 0.999 が3サンプル以上連続するランの回数と位置 |
| モノ互換 | L/R の位相相関係数(−1...+1)。モノラル音源は「モノ」と表示 |

- 外部ライブラリ(FFmpeg / libebur128 等)は導入しない。Swift + Accelerate(vDSP)の自前実装とし、既知テスト信号(正弦波、無音、フルスケール方形波、逆相ステレオ)に対する期待値をユニットテストで固定する。
- 解析は再生と完全に独立した低優先度の非同期タスクで行い、進捗と失敗を帳の中に明示する。解析の失敗・中断は再生に一切影響しない。
- 結果は `contentHash` + アナライザversion をキーに `library.json` へキャッシュし、同一音源の再解析を省く。旧 `library.json` は解析欄なしでそのまま読める(optional)。
- 旧データで `contentHash` が nil のトラックは、帳を開いた時点(または解析開始前)に既存のhash補完経路でSHA-256をbackfillしてからキャッシュキーを確定する。backfillに失敗した場合はキャッシュせず、その回の解析結果だけを表示する(失敗を無言にしない)。
- UI: トラック詳細/長押しから「狐火の帳」を開く。一画面に狐火の目盛(上表)を並べ、根拠付きの提案を最大数件表示する。絵巻は静的背景へ退く。VoiceOver で全指標が読め、Reduce Motion で追加の動きを持たない(帳はもともと静的)。

### 4.2 Phase B — A/B 参照

- 帳の中で参照トラックを1つ選び、ワンタップで A/B を切り替える。
- ラウドネスマッチ: Integrated Loudness の差から**減衰のみ**のマッチゲインを算出し、音量が大きい側を小さい側へ合わせる。`AVAudioPlayer.volume` は `0...1` で増幅できないため、ブースト方向のマッチは仕様上行わない。
- マッチゲインはユーザーの基準音量とは独立した乗数として扱い、実効音量 = 基準音量 × マッチ乗数 で適用する。既存の音量スライダー値を上書き・保存しないため、解除時は乗数を1.0へ戻すだけで基準音量が正確に復元される。
- 適用中はマッチ量(dB)を常時表示し、「マッチなし」へ即時に戻せる。帳を閉じる・再生を止める・トラックを変えると必ず解除される。
- ゲインは再生時調整のみで、ファイルにもライブラリにも書き込まない。

### 4.3 Phase C — チェックポイント

- `AudioTrack` に `checkpoints: [Checkpoint]?`(時刻 + 短いメモ)を追加し、`library.json` へ互換性を保って永続化する。
- 帳と通常再生画面から、チェックポイントへのシークと追加・削除ができる。先頭・サビ・ラスサビのような使い方を想定するが、名称は自由入力とし、曲構成の自動検出はしない。

### 4.4 Phase D — 取込動線

- 共有シート /「このAppで開く」(Open-in-place)からの直接取込。受け取ったファイルは既存の取込経路(アプリ内コピー + `ImportSummary`)へ流し、バウンス直後の音源を一手順で開けるようにする。

## 5. 非目標

- BPM・拍・サビ・曲構成の解析(§6 の線)。ラウドネス系の測定に限定する。
- マスタリング/修復処理、再生音への常時 DSP、Listening Profile(Step 3 の保留対象)。
- 外部ライブラリ・外部サーバー・外部送信。
- 図鑑・達成率・妖怪起点の逆引き。
- 帳の常時表示化。帳は明示的に開く検聴の場であり、通常の絵巻体験を置き換えない。

## 6. アーキテクチャ境界

- `KitsunebiAnalyzer`: 純粋なオフライン解析(ファイルURL → 指標)。再生系へ依存しない。
- `AnalysisStore`: `contentHash` キーのキャッシュと `library.json` 永続化。
- `TobariView`: 帳のUI。指標と提案の表示、A/B操作(Phase B以降)。
- `PlaybackController` は Phase B の volume 調整以外に変更しない。Audio Session・メータリング・Now Playing・reducer・residency へは触れない。

## 7. 検証

- **純粋ロジック:** K-weighting 係数、gating、LUFS/LRA/Peak の期待値を既知信号でユニットテスト。丸め・チャンク境界・極端に短い/無音のファイル・モノラル音源のエッジケースを含める。
- **回帰:** 既存フルスイート(再生・取込・行列・スプライト契約)を全て維持する。
- **Simulator:** 帳の表示、VoiceOver 読み上げ、Reduce Motion、絵巻が背景へ退く共存規則を確認する。
- 検証の証跡は Step 4 と同じ形式で `docs/evidence/step5-tobari/` に集約する。

## 8. 導入順序とゲート

1. **本仕様のユーザー承認**(この時点ではコードを書かない)。
2. Phase A: 解析エンジン + ユニットテスト → 帳UI → Simulator 検証 → ユーザー確認。
3. Phase B〜D を順に、各前段の検証後に着手する。
4. 完了の定義: §4.4 の項目が動き、**作者が自分のデモ確認に日常的に使っている**こと。
